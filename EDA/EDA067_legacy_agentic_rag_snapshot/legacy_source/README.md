# SIGNATE Agentic RAG Competition Workspace

SIGNATEのAgentic RAGコンペに取り組むための作業用プロジェクトです。  
共有ドライブ型の配布データを対象に、ファイル棚卸し、テキスト抽出、検索ベースライン、最終回答生成までを段階的に検証します。

## コンペ概要

本コンペは、NTTデータグループ主催3社による、AI人材とのマッチングを目的としたSIGNATEコンペです。  
課題は、架空のデータ分析コンサルティング会社「データアステル社」の社内AI担当として、共有ドライブに蓄積された案件資料から必要な情報を探し、社内から寄せられる質問に正確に回答するRAGシステムを構築することです。

通常の表形式データを用いた予測コンペではなく、社内資料検索・文書読解・表処理・画像読解・複数資料照合を含む、実務寄りのドキュメントQAコンペです。

## 課題の趣旨

生成AIの業務活用では、社内資料を正しく検索し、必要な情報を抽出し、根拠に基づいて回答する仕組みが重要になります。  
一方で、実務上の共有ドライブでは、資料の形式や粒度が統一されておらず、必要な情報が複数の場所に分散していることが多くあります。

本コンペでは、そのような実務に近い状況を想定し、以下のような能力を持つRAGシステムの構築が求められます。

- 必要な資料を探す
- 文書・表・画像・コードを読み取る
- 複数資料や複数案件にまたがる情報を照合する
- 社内用語や略称を必要に応じて解決する
- 質問で指定された回答形式、単位、小数桁、丸め方に従う
- 根拠のない回答や幻覚を避ける
- 未知の案件や資料が追加されても同じ処理方針で対応する

そのため、単純な「テキストをベクトル検索してLLMに渡す」だけでは不十分であり、ファイル形式ごとの抽出処理、構造化データ処理、画像・書式情報の扱い、検索結果の検証を組み合わせたAgentic RAGパイプラインが必要になります。

## 配布データの概要

データセットには、データアステル社が扱う複数業界の分析案件を想定した案件フォルダと、社内管理フォルダが含まれます。  
各フォルダには、提案・契約・進行管理・会議・報告・分析に関する資料やデータが格納されています。

主な特徴は以下です。

- 複数案件のフォルダが存在する
- 社内管理フォルダに、社内用語集や管理資料が含まれる
- ファイル形式や資料構造は統一されていない
- 文書、表、画像、コード、Notebookなど多様な情報を扱う必要がある
- 質問には、単一資料だけでなく複数資料の照合・集計が必要なものも含まれる

代表的な対象ファイル形式は以下です。

- `.md`
- `.csv`
- `.json`
- `.py`
- `.ipynb`
- `.docx`
- `.pptx`
- `.xlsx`
- `.pdf`
- `.png`

## 想定される質問タイプ

配布データの説明では、以下のようなタスクが想定されています。

- 単一資料からの記載内容抽出
- 複数資料・複数案件にまたがる情報の検索、照合、集計
- 社内用語・略称を含む質問への対応
- 用語集や社内管理資料の参照
- 回答形式、単位、小数桁、丸め方の指定に従った回答
- タスクID、アクションID、マイルストーンID、列名、パラメータ名などの識別子を資料表記どおりに回答
- 条件に該当する情報が存在しない場合は、該当なしであることを回答

注意点として、設問で明示されている場合を除き、社内用語・略称ではなく通常の表現で回答する必要があります。

## 評価方法

各質問に対する回答の質を、LLMである `gpt-5.2` が判定します。  
判定は1回のみ実行され、temperatureは0、シード固定とされています。ただし、微妙な回答内容では評価にわずかな揺らぎが発生する可能性があります。

スコアは各質問の得点平均で、範囲は `-1` から `1` です。

| 分類 | 得点 | 評価基準 |
|---|---:|---|
| Perfect | 1 | 質問に対して正確に答え、虚偽の内容が含まれていない回答 |
| Acceptable | 0.5 | 有用な答えだが、軽微な誤りが含まれている回答 |
| Missing | 0 | 「わかりません」「見つけられませんでした」など、具体的な答えがない回答 |
| Incorrect | -1 | 間違った、または関連性のない回答 |

この評価方法では、誤回答が `-1` になるため、根拠が弱いまま無理に答えることはリスクになります。  
一方で、Missingは0点であり、わからない回答ばかりではスコアが伸びません。したがって、検索・抽出・照合の精度を高めつつ、根拠が不十分な場合は無理に断定しない方針が重要です。

## 提出・制約

回答生成では、提供された未加工の共有ドライブ内データと質問文のみを入力として利用できます。  
また、コードで再現可能なRAGシステムとして実装する必要があります。

主な制約は以下です。

- 日本語での回答を前提とする
- 1回答あたり最大1000トークン
- 応答時間の制限は3時間
- 提供データと質問文のみを入力として利用する
- 特定質問だけに過度に依存した個別最適ではなく、未知資料にも対応できる処理方針が求められる

## 詳細ルールと実装上の遵守事項

本コンペでは、単に高いスコアを出すだけでなく、**コードで再現可能な汎用RAGシステム**として実装することが求められます。  
そのため、本プロジェクトでは以下のルールを前提に実装します。

### 参加・投稿に関する基本ルール

- チート行為や、コンペルールを無視した方法による参加は禁止
- 評価プロンプトをハックするような投稿は禁止
  - 高評価を返すような指示を回答に含める
  - 評価システム側に追加の処理や推論を行わせる指示を含める
- 質問への回答と関係のない投稿は禁止
- 他者への誹謗中傷、公序良俗に反する行為は禁止
- 悪質と判断された場合、入賞資格や会員資格の剥奪の可能性がある
- 利用できるアカウントは1人1アカウントのみ
- チーム人数は最大5人まで
- チーム作成・変更は `2026/8/5 23:59` まで

### 提出ファイルのルール

提出時は、必ず以下の形式にします。

```text
predictions.csv
```

この `predictions.csv` をzip形式に圧縮して提出します。  
zipファイル名は任意ですが、英数字、アンダースコア `_`、ハイフン `-` のみの使用が想定されています。

### 情報の取り扱い

コンペ開催期間中は、以下の情報をチーム外へ共有することは禁止されています。

- コード
- 学習済みモデル
- データ分析結果

ただし、すべての参加者が参照可能な公式フォーラムでの開示は可能です。

コンペ終了後は、情報公開ポリシーに従い、以下は公開可能とされています。

| 対象 | 公開可否 |
|---|---|
| モデル | 公開可 |
| 分析結果 | 公開可 |

ここでいうモデルには、実行単位のソースコードや学習済モデルが含まれます。  
分析結果には、提供データを用いて得られた知見、スニペット、集計量、加工データを含む解法などが含まれます。

### モデル構築の基本原則

本コンペで評価対象となるのは、**新規データが追加された場合でも、同じロジックで自動的に回答を生成できる手法**です。

そのため、以下を満たす必要があります。

- 提供された未加工の共有ドライブ内資料と質問文のみを入力にする
- 回答生成までの処理をコードで再現できるようにする
- 機械的な処理で、抽出・検索・読解・集計・回答生成を行う
- 新しい案件フォルダ、ファイル、質問が追加されても同じ処理方針で対応できるようにする
- 特定の設問や特定資料だけに合わせた個別最適化を行わない
- 人手による事前加工、手動回答、正解のハードコードを行わない

特に、以下のような情報をプロンプト、コード、設定ファイル、辞書、ルールベース処理に手入力することは禁止されています。

- 特定質問への回答
- 特定案件の金額、担当者名、ページ番号、セル番地
- 特定資料の抽出条件
- 正解候補
- 参照ファイル一覧
- 重要ページや重要セル

### 許可される処理の例

以下のような、汎用的・機械的な処理は許可されています。

- 提供された未加工データセットを実行時にプログラムで読み取る
- PDF、画像PDF、Excel、CSV、JSON、Notebook、Pythonコード、PowerPoint、Wordをファイル形式に応じて解析する
- テキスト、表、OCR結果、セル値、書式情報、画像情報、メタデータ、グラフ情報を機械的に抽出する
- OCR、表抽出、シート読取、グラフ解析、文書分割、コード解析、差分検出、書式抽出、ページ特定、セル特定を行う
- 抽出結果を、ベクトルDB、全文検索、SQL、DataFrame、ナレッジグラフなどに格納する
- 質問に応じて関連資料を検索し、抽出した根拠情報をLLMや回答生成処理に渡す
- 社内用語集を検索対象に含め、質問文中の社内用語・略称を通常表現へ展開する
- 設問で求められている計算、集計、比較、差分確認、条件抽出、ランキング作成をプログラムで実行する
- 外部ライブラリ、OCRエンジン、LLM API、埋め込みモデル、マルチモーダルモデル、エージェントフレームワークを利用する

### 禁止される処理の例

以下のような、特定設問や特定資料に合わせた処理は禁止されています。

- 提供データを人手で整理し、回答しやすい独自DBや一覧表を作って読み込ませる
- 質問ごとの正解候補、参照ファイル、重要ページ、重要セル、抽出条件を人手でまとめる
- 特定質問への回答や、特定案件の数値・名称・ページ番号・セル番地をコードやプロンプトに書く
- `record_id` や質問文を見て固定回答を返す
- 案件名やファイル名を見て、その案件・ファイル専用の値を返す
- 質問ごとに人がPDF、Excel、PowerPoint、NotebookLMなどを開いて回答を作成する
- NotebookLMなどのGUIツールへ質問を1問ずつ入力し、その出力を提出回答として使う
- 個別設問の正解を人手で確認し、その結果を回答生成用ルール、プロンプト、辞書、設定ファイルへ反映する
- 提供資料を検索・読解せず、外部知識、推測、LLMの事前知識だけで回答する
- 外部Web検索で取得した提供資料外の情報を、回答根拠として使う

ただし、案件名やファイル名を使った検索、ファイル形式に応じた抽出処理、フォルダ構造を利用した候補絞り込みなど、**新規データにも適用できる一般化された処理**であれば禁止事項には該当しません。

### データ利用のルール

回答根拠として使用できる情報は、提供された共有ドライブ内のフォルダ・ファイル群に含まれる情報に限られます。  
外部Web検索により、提供資料外の情報を取得して回答根拠にすることは禁止されています。

一方で、LLMモデルの学習、ファインチューニング、評価、企業実装などで外部データを使う場合は、利用規約・ライセンス・契約上、当該目的での商業利用が認められているデータに限り利用可能です。  
外部データを利用する場合は、最終提出物にデータソースやライセンス情報を明記する必要があります。

### ツール利用のルール

使用可能なツールは、商業利用が可能で、オープンなものに限定されます。  
Python、R、TensorFlowなどに加え、以下の利用は認められています。

- 外部ライブラリ
- OCRエンジン
- LLM API
- 埋め込みモデル
- 検索エンジン
- 表抽出ツール
- ローカルLLM
- マルチモーダルモデル
- エージェントフレームワーク

生成AIの使用自体に制限はありません。  
ただし、NotebookLMなどのGUIツールを手動操作して回答を作る方式は禁止です。提出コードと手順により、回答生成処理を再現できる必要があります。

### 回答生成時の注意点

最終回答では、以下を守る必要があります。

- 質問文で指定された回答形式、単位、小数桁、丸め方に従う
- 主略称の指定や抽出対象の表記に従う
- 条件に該当する情報や対象が存在しない場合は、該当なしであることを回答する
- 設問で明示されている場合を除き、社内用語・略称ではなく通常表現で回答する
- タスクID、アクションID、マイルストーンID、列名、パラメータ名などの識別子は資料上の表記どおりに回答する
- 単一資料だけでなく、複数資料・複数案件にまたがる検索、照合、集計にも対応する
- 社内用語や略称が含まれる場合は、共有ドライブ内の社内管理フォルダにある社内用語集を参照する

乱数、LLM出力、OCR結果などに揺らぎがある場合は、可能な範囲で以下を行います。

- seedを固定する
- ログを保存する
- 使用モデル名を記録する
- 抽出・検索・回答生成の中間結果を保存する

### 本プロジェクトでの反映方針

本プロジェクトでは、ルール違反を避けるため、以下の方針で進めます。

- validデータは評価・分析用途に使うが、特定回答をコードや辞書に埋め込まない
- 質問ごとの手動回答ファイルを作らない
- ファイル名・案件名・record_idに対する専用分岐を作らない
- 抽出処理はファイル形式単位で汎用化する
- 検索・抽出・計算・回答生成のログを保存する
- 外部Web検索結果を回答根拠に使わない
- GUIツールに1問ずつ入力して回答を作る運用はしない
- 提出用 `predictions.csv` は、再実行可能なコードから生成する

## 本プロジェクトの方針

このプロジェクトでは、最初から完全なAgentic RAGを作るのではなく、以下の順に段階的に検証します。

1. 共有ドライブ全体の構成を把握する
2. 機械的に読み取りやすいファイル形式からテキスト抽出する
3. 抽出テキストを使って検索ベースラインを作る
4. valid質問で、検索だけでどの程度根拠が拾えるか確認する
5. Office文書、PDF、Excel書式、画像、グラフなどの抽出を追加する
6. 検索・抽出・計算・回答生成を統合する

初期段階では、`.md`, `.csv`, `.json`, `.py`, `.ipynb` を対象にRAGの土台を作り、その後 `.docx`, `.pptx`, `.xlsx`, `.pdf`, `.png` へ広げます。

## 環境構築

`uv` を使う前提です。

```bash
uv sync
```

`uv run` がPython本体のダウンロードを始める場合は、ローカルに入っているPythonを指定します。

```bash
uv run --python 3.12 python EDA/EDA001/eda001.py
```

Windowsでは、日本語ファイル名かつ階層が深いデータを扱うため、最初は以下のような浅い場所に置くことを推奨します。

```text
C:\SIGNATE\SIGNATE_Agentic_RAG
```
